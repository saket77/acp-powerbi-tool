1. Executive summary
ACP consultants prepare Interactive Databooks in Power BI Desktop. The proposed portal lets
consultants create a client project, invite permitted viewers, upload a finished .pbix, preview it,
and release it. External clients sign in with multifactor authentication and view their
authorized Databooks within a branded ACP website; no Power BI authoring tools are required
for viewers.

The architecture separates the interactive website/API from background publishing work.
Azure Blob Storage provides private, temporary holding for uploaded files. Azure Queue
Storage and Azure Functions perform import, validation, release preparation, reminders, and
cleanup reliably. Microsoft Power BI Service hosts the actual reports and semantic models. This
is the app-owns-data embedding pattern.

What happens during a PBIX upload?
Blob stores the uploaded file privately; a queue triggers the Azure Function.
The Function imports the PBIX into the correct Power BI workspace, checks
the template and RLS, then stores report/model IDs for the portal.

4. Client onboarding and workspace lifecycle
     Authorized user creates a client record (for MVP, administrator-approved to avoid
      duplicates). The backend provisions a client-scoped service principal profile and
      workspace in Power BI and stores their IDs in Azure SQL.
     When another project is created for the same client, the backend REUSES that client
      workspace; its new .pbix becomes a separate semantic model/report pair.
     A client with multiple legal entities can have different viewing scopes. Project grants
      determine which users can view which project; Power BI RLS enforces which company-
      code rows are visible inside the project.
     Access expires with project/grant dates. A background timer manages notifications, expiry
      and retention, subject to ACP-approved policy.

Important: Azure Blob Storage is staging for the .pbix; it is NOT where clients query Power BI
visual data. Once imported, Power BI Service hosts the semantic model and report. For very
large .pbix files, Microsoft has a separate temporary-upload-location API; evaluate file sizes
before choosing the transfer method.



6. Viewing and data isolation
     Client signs in. The application resolves its user ID, active project grant, report version and
      permitted company codes server-side.
     The backend calls Power BI GenerateToken V2 for the exact report and semantic model,
      using the profile of that client and an appropriate effective identity/RLS role.
     The React Power BI SDK renders the interactive report in a managed iframe. The browser
      never receives the app/service principal credential.
     Company identifiers are stable codes in the Databook (the current proposal uses the FIN
      Tool “Ges.” code). The template needs Client and ACP roles; client RLS filters rows by
      permitted codes.
     Client workspaces provide tenant isolation; project/report scoping and RLS provide further
      isolation. Filters or hidden pages alone are NOT security controls.



7. Security and governance
     Explicit project grants (Lead, Member, Viewer, Client) rather than automatic access from
      seniority. Restricted engagements remain visible only to named members.
     Admin access to platform configuration does not imply silent access to client financials;
      emergency access must be time-limited and audited.
     Use managed identity in Azure where supported; limit every service principal profile to its
      own client workspace; do not persist credentials in the browser.
     Blob containers private, short-lived SAS, malware/content checks as applicable,
      configurable cleanup, encryption in transit/at rest; logs must omit financial values, secrets
      and embed tokens.
     Every authorization route must be tested across clients and projects; revoking access
      blocks new embed tokens, while previously issued tokens remain effective until expiry.
     ACP IT and privacy stakeholders must approve EU data residency, retention, security
      posture, client invitation policy and operational ownership.



8. MVP and success criteria
Partner demonstration scope: two fictional clients, two projects for one client, one
consultant/project lead, a second approver and two external viewers; one authentic template-
based Databook with 3–4 report pages or report types. The demonstration should exercise the
real integration, not a simulated iframe.

10. Proposed implementation sequence
Gate 1: prove service-principal profile → workspace creation → PBIX import and a working
client-scoped RLS embed using fictional data. Gate 2: implement uploads through Blob + queue-
triggered Function, validation, draft/release. Gate 3: add styled portal, project/user workflows
and admin health. Gate 4: security tests, EU hosting, operational handover and capacity pilot.
